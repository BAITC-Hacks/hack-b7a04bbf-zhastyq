# Граф денег — backend

Реализованы проверка трёх Parquet-файлов и полный CLI-расчёт ролей, кластеров и приоритетов в три CSV. Исходные файлы читаются без изменения.

## Установка и запуск

Python 3.10+ и uv, команды из каталога backend:

```bash
mkdir -p .tmp
uv venv --python python3 .venv
TMPDIR="$PWD/.tmp" uv pip install --no-cache --python .venv/bin/python -e '.[dev]'
.venv/bin/money-graph validate --data-dir data
```

Можно передать любой каталог с `nodes.parquet`, `edges.parquet`, `transactions.parquet`.
Для выданного набора результат:

```text
Статус: OK
Узлов: 2248
Рёбер: 3119
Транзакций: 4840
Seed: 81
```

Успех — exit code 0. Ошибка чтения или валидации — сообщение в stderr и exit code 1; неверные CLI-аргументы — exit code 2. Ошибки значений указывают файл, поле и номер строки с единицы (без заголовка). Ошибки схемы указывают файл и колонку. Сообщается первая найденная ошибка.

## Схемы и правила

| Файл | Обязательные колонки и типы Parquet |
|---|---|
| nodes | gid: int64, depth: знаковое целое, is_seed: bool |
| edges | src: int64, dst: int64, sum_kzt: float64, n_tx: int64, depth: int8 |
| transactions | src: int64, dst: int64, date: date32/date64, sum_kzt: float64 |

Дополнительные колонки не используются. Пропуски, повторяющиеся обязательные колонки и несовместимые типы отклоняются: строки с числами или датами не преобразуются автоматически.

Проверяются уникальность gid, наличие всех src/dst в nodes, уникальность пары src/dst в edges и наличие пары каждой транзакции в edges. Глубина nodes — 0–4, edges — 1–4; is_seed соответствует depth=0. n_tx — положительное целое. Суммы конечные и не меньше 5 000 KZT. Даты должны попадать в июль 2026 согласно описанию этой выборки.

Число узлов не фиксировано. Изолированные узлы и одинаковые транзакции сохраняются; пустые таблицы допустимы при наличии правильной схемы. gid не преобразуется в float, поэтому сохраняются длинные int64-идентификаторы.

Суммы представлены Decimal(str(value)) после чтения float64. Это сохраняет десятичное представление прочитанного значения без дальнейшей арифметики float, но не восстанавливает точность, потерянную при записи исходного float64. Округление до тиынов не выполняется.

## Путь команды

`bootstrap` связывает CLI, ValidateDataset и ParquetDatasetReader. CLI передаёт путь сценарию application; reader из infrastructure проверяет физическую схему и читает сущности domain. Сценарий вызывает domain-валидатор и возвращает DTO с количествами; CLI печатает сводку. Domain не зависит от PyArrow или внешних слоёв.

## Ограничения

Весь набор читается в память; потоковой обработки пока нет. Правила периода и порога фиксированы для описанной выборки. Сверка n_tx и суммы агрегированного ребра с транзакциями не реализована. Команда validate проверяет ссылки, не требует связности всего графа и не выводит графовые метрики; аналитический расчёт выполняет отдельная команда analyze.

HTTP API загрузки Parquet, просмотра и скачивания реализован (см. ниже). Чтение CSV не реализовано; AI-помощник требует настройки OpenAI; активный снимок не восстанавливается после перезапуска. Существующий `docs/data_contract.md` сохранён как контракт frontend, он обновлён для текущего HTTP API.

Данные, .env, .venv, временные файлы, кеши и результаты исключены через .gitignore. Правила разработки — в AGENTS.md.

## Анализ: роли, кластеры и топ-20

После установки зависимостей весь расчёт запускается одной командой:

```bash
.venv/bin/money-graph analyze --data-dir data --output-dir out
```

Команда использует тот же reader и domain-валидацию, что и `validate`. Затем сценарий application получает типизированные признаки и сообщества от NetworkX-адаптера, применяет domain-правила ролей и приоритетов, формирует описания кластеров и передаёт завершённый результат CSV-exporter. Время в сводке включает чтение, валидацию, расчёт и запись трёх файлов.

### Признаки и ограничения наблюдения

В направленный граф входят все nodes, в том числе изолированные; ребро направлено src → dst. Число входящих/исходящих контрагентов и суммы берутся из edges. Число отдельных входящих/исходящих операций берётся из transactions, включая одинаковые строки; n_tx из edges не добавляется к этому счётчику. Суммы из transactions повторно к обороту не прибавляются.

Соседние seed — разные узлы из объединения входящих и исходящих соседей, без самого узла. Отношение out/in рассчитывается только для не-seed с положительным наблюдаемым входом. Это отношение наблюдаемых потоков, а не полный баланс. Для seed оно не трактуется из-за неполных входящих. depth=4 при нуле исходящих — граница наблюдения, а не доказательство удержания денег. Изолированный узел получает peripheral и объяснение с нулевыми степенями.

### Роли: первое сработавшее правило

Обозначения: `I/O` — in_degree/out_degree; `S` — число соседних seed; `Vin/Vout` — суммы из edges; `r=Vout/Vin` — допустимое наблюдаемое отношение.

| Порядок | Роль | Правило | role_score |
|---|---|---|---|
| 1 | coordinator | I ≥ 3, O ≥ 3, S ≥ 2 | min(1, 0.6 + 0.05·min(I+O−6, 8)) |
| 2 | consolidator | I ≥ 3, Vin ≥ 100000 и r ≤ 0.6; для seed проверяются только I и Vin | min(1, 0.65 + 0.05·min(I−3, 7)) |
| 3 | distributor | O ≥ 5, Vout ≥ 100000 | min(1, 0.65 + 0.05·min(O−5, 7)) |
| 4 | transit | не-seed, I > 0, O > 0, 0.8 ≤ r ≤ 1.2 | 0.9 − abs(r−1) |
| 5 | terminal | I > 0, O = 0, depth < 4 | min(0.85, 0.55 + 0.05·min(I, 6)) |
| 6 | peripheral | ни одно предыдущее правило не сработало | 0.5 |

`role_score` — сила срабатывания выбранного эвристического правила в [0,1], не статистическая вероятность. Даже terminal означает лишь признаки получателя в доступной выборке. Evidence содержит числа, причину и ограничение наблюдения, не более 200 символов. Суммы в объяснениях компактно отображаются с шестью значащими цифрами; исходные признаки и CSV-оборот кластера не округляются до этого формата. Все выводы — гипотезы для проверки, без вывода о виновности.

### Приоритет

Четыре признака: `D=I+O`, `T=incoming_transactions+outgoing_transactions`, `V=Vin+Vout`, `S=seed_neighbors`. Для каждого признака отдельно вычисляется `L(x)=ln(1+x)`, затем `N(x)=L(x)/max(L(x))` по текущему набору. Если максимум равен нулю, нормированное значение равно нулю.

`priority_score = 0.35·N(D) + 0.25·N(T) + 0.25·N(V) + 0.15·N(S)`.

Диапазон [0,1]; значения сравнимы внутри одного набора, а не между разными выгрузками. Роль не добавляет скрытого бонуса. Для узла без связей и операций приоритет равен нулю. При self-loop операция/оборот учитываются и на входе, и на выходе как инцидентная активность узла. `why` показывает исходные признаки и вклад каждого в итоговый балл, а не повторяет роль.

Топ содержит min(20, число узлов) записей, порядок — убывание priority_score, затем возрастание числового gid. Тот же порядок используется для выбора до пяти top_gids кластера.

### Кластеры

Louvain (NetworkX 3.4.2), фиксированный seed=42, стандартная resolution=1. Узлы и рёбра добавляются в отсортированном порядке. Для поиска сообществ используется ненаправленная проекция: встречные суммы складываются в один вес. Для численной устойчивости все веса делятся на общий максимальный вес, что сохраняет относительные веса. Направление сохраняется для расчёта признаков и оборота.

Изолированные узлы образуют отдельные кластеры; для графа без рёбер каждый узел — отдельный кластер. Списки gid сообществ сортируются, затем сортируются сами списки; cluster_id нумеруются с 1. Повторный расчёт при той же версии библиотеки воспроизводим, включая перестановку строк входа. Между разными наборами стабильность cluster_id не обещается.

Внутренний оборот — сумма каждого исходного направленного ребра с концами в кластере ровно один раз, в том числе self-loop. Гипотеза содержит фактические размеры, seed, внутренний оборот и числа узлов с признаками сбора, распределения и координации. AI не используется.

### Выходные файлы

UTF-8, стандартное CSV-экранирование, фиксированный порядок колонок:

```text
nodes_roles.csv: gid,role,role_score,cluster_id,priority_score,evidence
clusters.csv: cluster_id,n_nodes,n_seed,sum_kzt_internal,top_gids,hypothesis
top_nodes.csv: rank,gid,role,priority_score,why
```

`top_gids` — JSON-массив целых gid внутри CSV-ячейки. При работе в JavaScript нельзя преобразовывать длинные gid в неточный Number. Пустой набор создаёт три файла с заголовками.

Сначала завершается расчёт, затем все CSV записываются во временный каталог внутри output-dir. Только после успешной записи заменяются три целевых файла; нерелевантные файлы не удаляются, символические ссылки вместо целевых CSV отклоняются. При обычной ошибке замены уже заменённые файлы восстанавливаются. Замена каждого файла атомарна, но транзакция сразу трёх файлов при аварийном завершении процесса/системы не гарантируется; одновременные запуски в один output-dir не поддерживаются.

### Границы текущего этапа

Расчёт в памяти, предназначен для выданного масштаба. Числовые суммы из float64 переводятся в Decimal без обещания восстановить точность источника; суммирование выполняется с precision=400 для диапазона этих исходных значений. Нет размеченных ролей и калибровки. Граф ограничен банком, июлем 2026, четырьмя коленами и порогом 5000 KZT; внешние поступления, остатки и переводы ниже порога неизвестны. Сверка сумм/n_tx edges с transactions пока не выполняется.

Реализованы воспроизводимый пайплайн, роли с объяснениями, кластеры и ранжированный CSV. Циклы, аномалии и устойчивость сети в текущем backend не реализованы. Временные наблюдения описаны ниже; frontend этой фичей не изменяется. AI-помощник описан ниже. HTTP API описан ниже.

## HTTP API для frontend

Установите обновлённые зависимости командой выше. Запуск из backend, строго один worker:

```bash
mkdir -p .tmp
TMPDIR="$PWD/.tmp" CORS_ORIGINS="http://localhost:5173,http://127.0.0.1:5173" \
  .venv/bin/uvicorn money_graph.bootstrap:create_api_app --factory \
  --host 127.0.0.1 --port 8000 --workers 1
```

Swagger: http://127.0.0.1:8000/docs. OpenAPI: http://127.0.0.1:8000/openapi.json.
Список CORS origins разделяется запятыми; по умолчанию пуст. ANALYSIS_STORAGE_DIR задаёт каталог CSV-версий (по умолчанию out/api). Переменные передаются в окружение процесса. Для чтения файла настроек явно добавьте `--env-file .env` (подробности ниже). Примеры без секретов — в .env.example.

```bash
curl http://127.0.0.1:8000/api/health
curl -F 'nodes=@data/nodes.parquet' \
     -F 'edges=@data/edges.parquet' \
     -F 'transactions=@data/transactions.parquet' \
     http://127.0.0.1:8000/api/analyze
curl http://127.0.0.1:8000/api/analysis
curl http://127.0.0.1:8000/api/nodes/100000008304139100
curl -OJ http://127.0.0.1:8000/api/exports/nodes_roles.csv
```

Полный актуальный контракт и JSON-примеры — [docs/data_contract.md](docs/data_contract.md). Согласованные изменения: HTTP gid/src/dst и top_gids — **строки**, вход только Parquet. Cluster_id, depth, rank и счётчики остаются числами. В domain gid по-прежнему int, CSV-схемы не изменены. Frontend не должен преобразовывать gid в Number.

Роуты обращаются к application-сценариям. PublishAnalysis берёт блокировку, файловый адаптер сохраняет три входа под фиксированными именами и считает фактические байты. Готовый AnalyzeDataset выполняется один раз в рабочем потоке, возвращая также исходные рёбра. После успешного расчёта CSV и удаления временных входов заменяется активный неизменяемый снимок. GetAnalysis, GetNode и GetExport читают одну версию за запрос; конкретное хранилище подключает bootstrap.

Ограничения: один активный анализ, один процесс/worker; после перезапуска требуется повторная загрузка. Лимит — 25 MiB на файл и 76 MiB на весь multipart-запрос. Второй пересчёт возвращает 409 ANALYSIS_BUSY; при ошибке старый анализ остаётся доступен. CSV хранятся раздельно для каждой версии; старые версии автоматически не удаляются. При обновлении между двумя GET-запросами frontend сверяет analysis_id/X-Analysis-Id. Авторизация и постоянное хранение снимка не реализованы; сервер предназначен для локального MVP.

Маршрут /api/ask реализован; ai_configured отражает наличие полной настройки OpenAI. CSV-вход, frontend и дополнительная аналитика в этот этап не входят. Команды validate и analyze продолжают работать независимо от HTTP-сервера.

## Полнота наблюдения и дополнительные проверки

`GET /api/nodes/{gid}` сохраняет прежние поля и добавляет `data_gaps` (код, описание, фактическое основание) и `next_requests` (связанный код, запрос данных, цель проверки). Это рекомендации аналитику; никаких внешних запросов, LLM или новых аналитических расчётов при открытии карточки нет. Полный JSON-пример и коды — в [контракте карточки](docs/data_contract.md#get-apinodesgid).

Применяются все подходящие правила в фиксированном порядке:

1. **depth=4 без исходящих:** объяснить обрыв наблюдения, запросить исходящие за границей обхода; удержание средств не доказано.
2. **Seed:** запросить полные входящие за тот же период; out/in не трактуется как достоверный баланс.
3. **Изолированный узел:** проверить полноту выгрузки и исключения при сборе; отсутствие деятельности не утверждается.
4. **Исходящий оборот больше входящего:** сравнение Decimal без деления и дополнительных порогов; запросить остатки и полную выписку. Возможны начальный остаток или отсутствующие поступления, это не доказанная аномалия.
5. **Общие ограничения:** внутрибанковские переводы, порог 5000 KZT, июль 2026, неизвестные остатки. Рекомендуются сведения о межбанковских и малых переводах, выписки за согласованные соседние периоды и остатки. Наличие исключённых операций не утверждается.

Предупреждения о границе и изоляции используют общую `observation_policy`. Путь карточки: HTTP → GetNode → один снимок анализа → assess_observation в domain → HTTP-схема. Коды уникальны и связаны с рекомендациями один к одному; сначала идут ограничения узла, затем общие. Если остатки уже запрошены для OUTFLOW_EXCEEDS_INFLOW, отдельный BALANCES_UNAVAILABLE не добавляется. Прежнее поле limitations, роли, приоритеты и CSV не меняются.

Процент полноты не рассчитывается: объём неизвестных операций неизвестен. Общие условия взяты из контракта исходной выборки, а не определены по наблюдаемому минимуму суммы или диапазону дат. Рекомендации помогают проверить гипотезу, не доказывают её.

|---|---|---|
| 100000000018102100 | depth=4, входов=1, выходов=0, вход=7000 KZT | Исходящие за границей обхода |
| 100000000343175100 | Seed, вход=178712 KZT, выход=4000039 KZT | Полные входящие, остатки и полная выписка |

## AI-помощник: POST /api/ask

Реализован один адаптер — OpenAI Responses API. Имя модели приложения задаётся отдельно от модели Codex CLI. Выберите модель, доступную вашему OpenAI-проекту и поддерживающую Responses API со Structured Outputs. Второй провайдер не добавлен.

Настройки окружения:

| Переменная | Назначение |
|---|---|
| OPENAI_API_KEY | Ключ команды; обязателен, не записывать в репозиторий и логи |
| OPENAI_MODEL | Доступное аккаунту имя модели; обязательно, значения по умолчанию нет |
| OPENAI_BASE_URL | HTTPS-адрес OpenAI API, по умолчанию https://api.openai.com/v1; задавайте только доверенный адрес |
| OPENAI_TIMEOUT_SECONDS | Таймаут, по умолчанию 30 секунд; допустимо 1–120 |

Приложение читает окружение при создании API. Файл настроек загружает Uvicorn через явный `--env-file` до создания приложения; необходимый python-dotenv входит в зависимости проекта. Автоматического поиска `.env` в родительских каталогах нет. Уже заданные переменные окружения имеют приоритет над файлом. После изменения настроек перезапустите сервер.

Запуск из backend с локальным `backend/.env`:

```bash
mkdir -p .tmp
TMPDIR="$PWD/.tmp" .venv/bin/uvicorn money_graph.bootstrap:create_api_app --factory \
  --env-file .env --host 127.0.0.1 --port 8000 --workers 1
```

Если файл команды расположен в корне проекта, используйте `--env-file ../.env` вместо `--env-file .env`. Укажите реально существующий файл. Не загружайте его через `source` и не выводите содержимое: python-dotenv читает настройки без выполнения shell-команд. Не добавляйте файл с секретами в Git; `backend/.env` исключён через backend/.gitignore. Корневой файл находится вне области этого правила и также не должен попадать в коммиты.

Параметр описан в [документации Uvicorn](https://www.uvicorn.org/settings/#application). `GET /api/health` возвращает ai_configured=true только при наличии ключа, модели и корректных URL/таймаута; это не проверка доступности сервиса или прав на модель. Без конфигурации `/api/ask` отвечает 503, остальной API работает.

После загрузки данных скопируйте текущий analysis_id из ответа `/api/analyze` или `/api/analysis`:

```bash
curl -X POST http://127.0.0.1:8000/api/ask \
  -H 'Content-Type: application/json' \
  -d '{"analysis_id":"ЗАМЕНИТЕ_ТЕКУЩИМ_ID","question":"Почему этот узел в топе?","context_gids":["100000003684369100"]}'
```

Поддерживаемые вопросы: причины приоритета, причины роли, наблюдаемые получатели выбранных узлов. Вопрос — 1–2000 символов после strip; выберите 1–5 уникальных существующих gid. Без выбранного узла API просит выбрать его на графе. HTTP-идентификаторы всегда строки.

Путь запроса: API-схема → AskQuestion → один снимок из существующего GetAnalysis → отбор фактов → LanguageModel → OpenAI-адаптер → проверка структуры и ссылок → сбор серверных references/limitations. Синхронный маршрут выполняется FastAPI в рабочем потоке, не в async event loop. Версия анализа проверяется до вызова и после ответа/ошибки провайдера. При замене снимка возвращается 409 STALE_ANALYSIS.

Модель получает только выбранные узлы, до пяти непосредственных соседей и до десяти связанных рёбер, максимум 32 KiB JSON-контекста. Сначала отбирается крупнейшее исходящее ребро каждого выбранного узла, затем остальные близкие рёбра по убыванию суммы и стабильному порядку src/dst. Это отбор контекста из готовых результатов, без изменения аналитических правил. Роли, оценки, evidence, причины приоритета, топ-позиции и агрегаты берутся из расчёта; полный граф и сырые транзакции провайдеру не отправляются. При усечении связей limitations содержит число показанных и доступных близких рёбер; ответ не должен выдавать выборку за полный список контрагентов.

Ответ провайдера — строгий JSON `answer` и `referenced_gids`. Проверяются непустой текст до 6000 символов, 1–10 уникальных строковых ссылок из переданного контекста. Дополнительно отклоняются явно записанные `gid=...` и непрерывные числа из 16–19 цифр, не включённые в ссылки. Такая консервативная проверка может отклонить крупную денежную сумму в свободном тексте. `references[].facts` и `limitations` формируются сервером из снимка, а не моделью. Результат не меняет роли, приоритеты и CSV.

**Проверка ссылок не гарантирует истинность всего свободного текста.** Модель может ошибиться в интерпретации, ответ не является доказательством виновности; аналитик должен сверять его с facts и карточками. Вопрос и данные передаются как недоверенный пользовательский контекст, отдельно от инструкций. Инструкции требуют русского языка, ограничений выборки и запрещают выдумывать клиентов, операции, атрибуты и виновность. Frontend должен отображать answer как обычный текст, не исполнять его как HTML.

Один вопрос вызывает не более одного обращения к провайдеру, автоматических повторов нет. Используется store=false, ограничены таймаут, число выходных токенов и размер HTTP-ответа (128 KiB). Отказ, таймаут, неверный JSON или неподтверждённые ссылки дают 503 AI_UNAVAILABLE без сырых ошибок провайдера. При ошибках входа — 422 INVALID_QUESTION, до загрузки анализа — 404 NO_ANALYSIS.

Формат адаптера сверён с [официальной документацией Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs) и [Responses API](https://developers.openai.com/api/docs/guides/migrate-to-responses). Автоматические тесты используют только fake-модель и httpx.MockTransport; внешний HTTP заблокирован тестовой фикстурой.

Приёмка 23.09.2026: с явным `--env-file ../.env` выполнен один реальный вызов OpenAI через `/api/ask`, модель `gpt-6-luna`, HTTP 200 за 8,04 секунды. Перед ним исходные Parquet загружены через `/api/analyze`: 2248 узлов, 3119 рёбер, 88 кластеров. Ответ для seed-узла `100000003684369100` объяснил consolidator через 24 плательщика, 58 входящих операций и 3 848 436 KZT. Числа и направления связей сверены с карточкой; все шесть ссылок — точные существующие строковые gid. Учтены неполные входящие seed и усечение контекста до 5 из 86 близких рёбер; утверждений о виновности нет. После вызова граф, карточка и три CSV доступны. Это результат одного вызова, не гарантия доступности сервиса и правильности будущих ответов.

## Временные наблюдения

Полный анализ (`money-graph analyze --data-dir data --output-dir out` или `POST /api/analyze`) теперь однократно рассчитывает временные наблюдения по уже прочитанным transactions. Агрегаты edges остаются источником прежних ролей и приоритетов. Снимок хранит типизированные результаты; `GET /api/nodes/{gid}` не перечитывает Parquet. Новых CSV и маршрутов нет.

- **rapid_outflow:** внешние входящие за день D и внешние исходящие за D+1/D+2. Один результат на узел и D, с суммами, числами операций и интервалами. Self-loop исключён. Это кандидат для проверки транзита, не доказательство перечисления именно полученных денег. Окна могут пересекаться — их обороты нельзя суммировать как независимые.
- **synchronized_inflow:** минимум три разных внешних отправителя в один день; показаны все их точные gid, количество операций и сумма. Повторные операции не увеличивают число отправителей, self-loop исключён. Совпадение дат не доказывает координацию.
- **activity_spike:** минимум пять операций за день и минимум тройное превышение среднего. Среднее = все операции узла / 31 календарный день июля 2026, включая дни без операций. Входящие и исходящие учитываются вместе, self-loop один раз, включая сумму. Показаны среднее, коэффициент и пороги. Это эвристика относительно той же выборки, не доказанная подозрительность.

Даты границ периода общие с валидацией (`observation_policy`), окно не сокращается до дней активности. Деньги суммируются как Decimal с precision=400; HTTP-числа имеют прежние ограничения отображения float64. Даты не содержат времени: внутри одного дня порядок операций неизвестен. За пределами периода операции неизвестны, входящие seed неполны. Ограничения входят в каждое наблюдение; усечённое концом периода окно rapid_outflow отмечено отдельно.

В карточке `temporal_patterns.items` содержит первые 50 результатов в порядке даты по возрастанию, затем rapid_outflow → synchronized_inflow → activity_spike. `total_count` — полное число находок узла, `truncated=true` означает усечение. `/api/analysis.temporal_summary` содержит полные счётчики трёх видов и `n_nodes` — количество уникальных узлов с находками, до усечения карточек. Точные типы полей и JSON-примеры — в [контракте](docs/data_contract.md#временные-наблюдения-фича-6).

Frontend может добавить в существующую карточку блок «Временные наблюдения»: заголовок вида, дата, показатели, explanation и limitations. sender_gids остаются строками и могут открывать карточки отправителей. При пустом items показывать «В этой выборке наблюдений не найдено», при truncated — «Показаны первые 50 из total_count». Не суммировать деньги между наблюдениями и не превращать находки в утверждение виновности. Frontend-код не изменялся.

Проверка исходного набора через HTTP: полный анализ с созданием CSV — 6,297 с (лимит 300 с); rapid_outflow=669, synchronized_inflow=66, activity_spike=159, узлов с наблюдениями=331. CSV содержат 2248 / 88 / 20 строк данных. Максимум находок узла — 23; усечение проверено отдельно на синтетическом наборе с 61 находкой.
