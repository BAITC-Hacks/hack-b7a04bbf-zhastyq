# Граф денег — backend

Локальный анализ направленной сети переводов. Один сценарий приложения обслуживает CLI и HTTP API. Роли и приоритеты — объяснимые гипотезы для проверки, не вероятность виновности.

## Запуск

Python 3.10+ в Linux или WSL:

```bash
cd backend
uv venv --python 3.10
uv pip install --python .venv/bin/python -e '.[dev]'
.venv/bin/money-graph analyze --data-dir data --out out
```

Последняя строка — основной запуск после установки зависимостей. Поместите `nodes.parquet`, `edges.parquet`, `transactions.parquet` из выданного архива в `backend/data/`. Оригиналы в Downloads не изменяются. Файлы данных и токены игнорируются Git.

Для локального API:

```bash
.venv/bin/money-graph serve --data-dir data --out out
```

API доступен по `http://127.0.0.1:8000`; сервер принимает новую тройку файлов через `POST /api/analyze`. Можно указать каждый путь отдельно вместо `--data-dir`:

```bash
.venv/bin/money-graph analyze --nodes /path/nodes.csv --edges /path/edges.parquet --transactions /path/transactions.csv --out out
```

Поддерживаются CSV (UTF-8, заголовок, запятая, дата `YYYY-MM-DD`) и Parquet в любой комбинации. Нужны `nodes(gid,depth,is_seed)`, `edges(src,dst,sum_kzt,n_tx,depth)`, `transactions(src,dst,date,sum_kzt)`. Дополнительные колонки игнорируются. Проверяются типы, уникальность `gid` и пар, ссылки на узлы, количество и сумма транзакций по каждой паре. Ошибка не заменяет действующий анализ.

## Результаты

После запуска в `out/` находятся `nodes_roles.csv`, `clusters.csv`, `top_nodes.csv`, `viewer_data.json`. Они ссылаются на одну опубликованную версию анализа. Новая версия становится активной только после полной записи.

| Файл | Содержимое |
|---|---|
| `nodes_roles.csv` | Каждый `gid`, роль, `role_score`, `cluster_id`, `priority_score`, числовое `evidence`, глубина, признак seed и наблюдаемые входящие/исходящие метрики |
| `clusters.csv` | `cluster_id`, размер, число seed, сумма рёбер внутри кластера, ключевые `gid`, гипотеза |
| `top_nodes.csv` | До 20 существующих узлов, убывающий приоритет, объяснение |
| `viewer_data.json` | Полный граф и расширенная аналитика для интерфейса |

Исходный набор дал 2 248 узлов, 3 119 рёбер, 4 840 транзакций, 81 seed и 444 узла на границе четвёртого колена. Изолированные seed входят в результат. Размер нового набора в коде не фиксирован.

## Правила ролей

Метрики считаются только по наблюдаемым направленным рёбрам. `in_deg` и `out_deg` — разные контрагенты, `in_kzt` и `out_kzt` — суммы, `in_tx` и `out_tx` — числа переводов, `seed_neighbors` — разные соседние seed. Для не-seed `ratio = out_kzt / in_kzt` при положительном входе. Для seed отношение не используется: внешние входящие не выгружены.

Правила применяются сверху вниз; первое сработавшее назначает основную роль:

1. `coordinator`: `in_deg ≥ 3`, `out_deg ≥ 3`, `seed_neighbors ≥ 2`.
2. `consolidator`: `in_deg ≥ 3`, `in_kzt ≥ 100 000`, и `ratio ≤ 0.6` для не-seed. Для seed проверяются только наблюдаемые входящие связи и сумма, без отношения.
3. `distributor`: `out_deg ≥ 5`, `out_kzt ≥ 100 000`.
4. `transit`: не-seed с входом и выходом, `0.8 ≤ ratio ≤ 1.2`.
5. `terminal`: `in_deg > 0`, `out_deg = 0`, `depth < 4`.
6. `peripheral`: остальные, включая обрезанный графом узел `depth = 4` без исходящих.

`role_score` — ограниченная `[0,1]` сила срабатывания правила, не калиброванная вероятность. Для `coordinator`: `0.55 + 0.05·min(in_deg,5) + 0.05·min(out_deg,5)`; для `consolidator`: `0.55 + 0.07·min(in_deg−2,5) + 0.05·min(in_kzt/100000,2)`; для `distributor`: `0.55 + 0.05·min(out_deg−4,6) + 0.05·min(out_kzt/100000,2)`; для `transit`: `0.8−|ratio−1|`; для `terminal`: `0.55+0.08·min(in_deg,5)`; для `peripheral`: `0.5`. Результат ограничивается `[0,1]`. `evidence` содержит исходные числа и отметку границы обхода, максимум 200 символов.

Базовый приоритет равен `0.35·ln(1+in_deg+out_deg) + 0.25·ln(1+in_tx+out_tx) + 0.2·ln(1+in_kzt+out_kzt) + seed_neighbors + 0.75·[coordinator]`. `priority_score` — базовый приоритет, делённый на максимум по текущему набору. При равенстве выше узел с меньшим `gid`.

Кластеры вычисляются Louvain на ненаправленной проекции с суммой весов встречных рёбер. Это группировка близости, не направление движения денег. Внутренний оборот кластера — сумма исходных направленных рёбер, у которых оба конца в этом кластере.

## Дополнительная аналитика

- `truncated_by_depth`: `depth ≥ 4` и ноль наблюдаемых исходящих. Такой узел не получает роль `terminal` по одному этому признаку.
- `rapid_transit`: вход и выход одного узла в тот же день или через 1–2 дня, с датами и суммами; это не доказательство движения одних денег.
- `activity_spike`: минимум 3 наблюдаемых перевода за день и не менее трёх средних дневных количеств за диапазон дат набора.
- `synchronized_inflow`: в один день пришли переводы от двух или более разных плательщиков.
- `repeated_routes`: цепочка `A→B→C`, где каждое из двух рёбер встречается минимум в двух отдельных транзакциях; показывается нижняя оценка повторений. Связь конкретных переводов не установлена.
- `cycles`: наблюдаемые направленные циклы длиной 2–4 ребра, максимум 100 для быстрого просмотра. Цикл не доказывает возврат тех же денег.
- `observed_splitting`: минимум три перевода по 5 000–9 999 KZT по одной паре с суммой не меньше 20 000 KZT. Переводы ниже порога выгрузки не видны.
- `unusual_out_degree`: `out_deg ≥ max(3, 3·median(out_deg))` среди узлов того же колена и выше медианы. Показаны колено, медиана, порог и число аналогов.
- `robustness`: число слабосвязных компонент и размер крупнейшей до/после удаления `N=min(5,max(1,⌊n_nodes/100⌋))` узлов с высшим приоритетом.
- Карточка любого `gid` содержит роль, метрики, до 50 крупнейших входящих/исходящих связей, временные и аномальные признаки, маршруты, пробелы данных и конкретный следующий запрос.

Глобальные списки временных событий и аномалий в JSON ограничены первыми 500, маршрутов и циклов — первыми 100; карточка сохраняет до 20 событий каждого типа для узла.

## API

Полный контракт — [`docs/data_contract.md`](docs/data_contract.md). Основные маршруты:

- `GET /api/health`, `GET /api/analysis`, `GET /api/nodes/{gid}`;
- `POST /api/analyze` — multipart поля `nodes`, `edges`, `transactions`;
- `POST /api/ask` — JSON `{analysis_id, question, context_gids}`;
- `GET /api/exports/nodes_roles.csv`, `/api/exports/clusters.csv`, `/api/exports/top_nodes.csv`.

Ошибки возвращают `{error:{code,message,details}}`. При неверной схеме — 422 с недостающими колонками; старый анализ остаётся доступным. Идентификаторы `gid` в исходных данных имеют 18 цифр: клиентский JavaScript должен сохранять их точно, поскольку обычный `Number` не гарантирует точность таких целых чисел.

## ИИ

Настройте переменные окружения, не записывая секреты в репозиторий:

```bash
export LLM_PROVIDER=openai
export OPENAI_API_KEY=... 
export OPENAI_MODEL=...
```

Или `LLM_PROVIDER=nvidia`, `NVIDIA_API_KEY`, `NVIDIA_MODEL`. При необходимости задайте `OPENAI_BASE_URL` или `NVIDIA_BASE_URL`. По умолчанию используются [OpenAI Responses API](https://platform.openai.com/docs/api-reference/responses) и [NVIDIA Chat Completions API](https://docs.api.nvidia.com/nim/re/reference/llm-apis). Реальная модель должна быть доступна выданному токену; имя модели выбирается по его условиям. При отсутствии конфигурации `/api/ask` возвращает 503, а расчёт графа остаётся доступным.

Сценарий вопроса сначала выбирает узлы, связи и топ-позиции из текущего анализа, затем отправляет ограниченные факты модели. Ответ с посторонним `gid` отклоняется. Модель не изменяет роли, приоритеты и выгрузки. Поддерживаемые вопросы: почему `gid` в топе, куда идут деньги от `gid`, кто получает деньги от выбранных seed. `analysis_id` защищает от ответа по устаревшему набору.

## Проверки и демо

```bash
.venv/bin/pytest -q
```

Тесты проверяют правила ролей, атомарную публикацию, ошибки схемы, CSV/Parquet, API, расширенную аналитику и реальный набор, если файлы в `data/`. Короткий пятиминутный сценарий:

1. Запустить `money-graph serve --data-dir data --out out` и открыть `GET /api/analysis`.
2. Показать топ-узлы `100000005382566100` и `100000008733194100`; открыть `/api/nodes/{gid}` и объяснить наблюдаемые числа.
3. Найти изолированный seed `100000000456947100` и узел границы `100000000018102100`.
4. Загрузить новую тройку CSV через `/api/analyze`, затем скачать три выгрузки.
5. При настроенном и проверенном токене задать живой вопрос через `/api/ask` с текущим `analysis_id`.

## Границы вывода и рост данных

Видны только внутрибанковские исходящие переводы от 81 seed на четыре колена за июль 2026, минимум 5 000 KZT. Внешние поступления seed, операции ниже порога, остатки, идентификационные атрибуты и размеченные роли отсутствуют. Баланс и связь конкретных денег между рёбрами не выводятся.

При росте до примерно миллиона узлов чтение и агрегирование следует вести потоково по Parquet, хранить adjacency в компактном формате и перенести Louvain/центральность на igraph или распределённый движок. API должен отдавать выбранный подграф и страницы карточек, а не весь JSON сети; версии публикации и индексы `gid` нужно хранить отдельно. Текущий NetworkX и полный JSON рассчитаны на размер выданного набора.
