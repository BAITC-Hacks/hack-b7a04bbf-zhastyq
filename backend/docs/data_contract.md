# HTTP-контракт frontend/backend — MVP v3

Согласованные изменения: **все клиентские идентификаторы в HTTP JSON — десятичные строки; загрузка только Parquet**. Корневая копия docs/data_contract.md пока не обновляется и содержит старый контракт. Для текущей интеграции используйте этот документ.

API: `http://127.0.0.1:8000`; Swagger: `http://127.0.0.1:8000/docs`.
В Compose frontend/Nginx проксирует `/api` на backend с сохранением пути; браузер использует относительные URL. Swagger доступен на том же origin по `/docs`. При отдельном размещении frontend CORS задаётся списком origins через CORS_ORIGINS.

Не преобразовывайте gid/src/dst в JavaScript Number. Сравнивайте и передавайте их как строки. Это касается узлов, рёбер, карточки, top_nodes и clusters.top_gids. cluster_id, depth, rank, n_tx и счётчики — JSON-числа. Суммы в KZT — JSON-числа для отображения; HTTP не гарантирует дополнительную точность денег относительно float64 источника. Domain хранит int/Decimal, CSV содержит точные десятичные gid.

## Сценарий

1. GET /api/health или GET /api/analysis. До загрузки анализа нет.
2. POST /api/analyze с тремя Parquet-файлами; дождаться успешного расчёта.
3. GET /api/analysis возвращает полный граф, включая изолированные узлы, кластеры и топ.
4. GET /api/nodes/{gid} возвращает карточку и все её направленные связи.
5. GET /api/exports/{name} скачивает CSV текущего снимка.

6. POST /api/ask принимает вопрос и 1–5 выбранных строковых gid текущего анализа.

## GET /api/health

200, до первой загрузки:
```json
{
  "status": "ok",
  "analysis_ready": false,
  "ai_configured": false
}
```

После успешной загрузки analysis_ready=true. ai_configured отражает полную настройку OpenAI (ключ, модель, корректные URL и таймаут), но не гарантирует доступность провайдера.

## POST /api/analyze

multipart/form-data, ровно три файловых поля, без дубликатов и дополнительных полей:

| Поле | Обязательные Parquet-колонки |
|---|---|
| nodes | gid, depth, is_seed |
| edges | src, dst, sum_kzt, n_tx, depth |
| transactions | src, dst, date, sum_kzt |

Имена приложенных файлов должны оканчиваться на .parquet; содержимое проверяется как Parquet. Клиентские имена не используются как пути. Лимит 25 MiB (26 214 400 байт) на файл проверяется по фактически прочитанным байтам. Общий HTTP body ограничен 76 MiB с учётом multipart. Типы, пропуски и правила выборки проверяются существующим validate; дополнительные колонки не используются.

Успех — 200 после полного расчёта и подготовки CSV. Пример ниже рассчитан на синтетическом наборе из четырёх узлов, включая два различных gid, которые нельзя точно хранить как Number:
```json
{
  "analysis_id": "example-analysis",
  "status": "ready",
  "summary": {
    "n_nodes": 4,
    "n_edges": 3,
    "n_transactions": 4,
    "n_seed": 2,
    "n_clusters": 2,
    "edge_volume_kzt": 20000.0
  },
  "analysis_url": "/api/analysis"
}
```

Числа не фиксированы. Для выданного набора ожидаются 2248 узлов, 3119 рёбер, 4840 транзакций, 81 seed; число кластеров и оборот возвращаются по расчёту.

analysis_id меняется при каждом успешном расчёте. При ошибке прежний снимок и его CSV остаются доступны. Параллельный пересчёт возвращает 409 ANALYSIS_BUSY; GET-запросы продолжают отдавать предыдущий снимок.

## GET /api/nodes/{gid}

Параметр gid — десятичная строка int64. Ответ содержит analysis_id, node, incoming, outgoing, limitations, data_gaps, next_requests и temporal_patterns. Прежние поля и их смысл сохранены. Входящие связи имеют dst=gid, исходящие — src=gid; ограничения количества связей нет. Self-loop будет в обоих списках. Пример узла на границе наблюдения:

Неизвестный gid — 404 GID_NOT_FOUND; неверная запись gid — 422 INVALID_SCHEMA; до загрузки — 404 NO_ANALYSIS.

`data_gaps[]` содержит `code`, `description`, `evidence`; `next_requests[]` — `gap_code`, `request`, `reason`. Все эти поля — непустые строки. Каждый `gap_code` соответствует ровно одному `data_gaps[].code`; обе коллекции имеют одинаковый стабильный порядок. Рекомендации выполняет аналитик вручную: API не запрашивает дополнительные данные автоматически.

Порядок правил (применяются все подходящие, специфичные для узла идут первыми):

| Код | Основание и рекомендуемая проверка |
|---|---|
| DEPTH_BOUNDARY | depth=4 и out_deg=0: запросить исходящие за границей обхода за тот же период; отсутствие исходящих не доказывает удержание |
| SEED_INCOMING_INCOMPLETE | is_seed=true: запросить полную историю входящих; out/in не является достоверным балансом |
| ISOLATED_NODE | in_deg=out_deg=0: проверить полноту выгрузки и исключения при сборе; отсутствие связей не доказывает отсутствие деятельности |
| OUTFLOW_EXCEEDS_INFLOW | out_kzt > in_kzt, точное сравнение Decimal: запросить остатки и полную выписку; возможны начальный остаток или ненаблюдаемые поступления, это не доказанная аномалия |
| INTRABANK_ONLY | Внутрибанковская выборка: запросить сведения о межбанковских переводах за тот же период |
| AMOUNT_THRESHOLD | Порог 5000 KZT: запросить операции ниже порога за тот же период |
| LIMITED_PERIOD | Июль 2026: запросить выписки за согласованные соседние периоды для проверки применимости гипотезы |
| BALANCES_UNAVAILABLE | Нет остатков в исходных таблицах: запросить начальные и конечные остатки |

Если есть OUTFLOW_EXCEEDS_INFLOW, отдельный BALANCES_UNAVAILABLE не добавляется: первый уже объясняет неизвестность остатков и содержит запрос на их получение. Остальные независимые ограничения сохраняются вместе; коды и рекомендации не повторяются. Evidence общих ограничений описывает условия сбора, а не доказывает существование исключённых операций. Межбанковские операции и переводы ниже порога могли отсутствовать в выборке; их фактическое наличие не утверждается.

Это локальные правила по одному снимку анализа, без LLM и без процента полноты: полный объём неизвестных операций не известен. Роли, приоритеты, HTTP gid и CSV-схемы не изменены. Ограничения исходной выборки (период, порог, банк) фиксированы текущим контрактом набора, не выводятся из минимума/максимума наблюдаемых операций.


## GET /api/exports/{name}

Разрешены только nodes_roles.csv, clusters.csv, top_nodes.csv. Успех — 200, Content-Type: text/csv; charset=utf-8, Content-Disposition: attachment; filename="...". Заголовок X-Analysis-Id указывает версию скачанного снимка и доступен frontend через CORS. Схемы CSV сохранены по ТЗ; top_gids в CSV — JSON-массив целых, а в HTTP — массив строк.

Неизвестное имя или путь — 404 EXPORT_NOT_FOUND. До загрузки разрешённого файла — 404 NO_ANALYSIS. Отдельные HTTP-запросы могут попасть на разные версии, если между ними закончился новый расчёт: сравнивайте analysis_id/X-Analysis-Id и обновляйте экран.

## Ошибки

Единый формат, без traceback и внутренних путей:

```json
{
  "error": {
    "code": "INVALID_SCHEMA",
    "message": "nodes.parquet: поле gid: обязательная колонка отсутствует или повторяется",
    "details": {"file": "nodes.parquet"}
  }
}
```

| HTTP | code | Причина |
|---|---|---|
| 404 | NO_ANALYSIS | Нет активного анализа |
| 404 | GID_NOT_FOUND | Неизвестный gid |
| 404 | EXPORT_NOT_FOUND | Недопустимый или отсутствующий экспорт |
| 422 | INVALID_SCHEMA | Форма, формат, схема или значения неверны |
| 413 | FILE_TOO_LARGE | Превышен лимит файла/запроса |
| 409 | ANALYSIS_BUSY | Другой анализ выполняется |
| 409 | STALE_ANALYSIS | Анализ заменён до или во время ответа AI |
| 422 | INVALID_QUESTION | Вопрос или выбранные gid некорректны |
| 503 | AI_UNAVAILABLE | Нет конфигурации, ошибка/таймаут модели или неверный ответ |
| 500 | INTERNAL_ERROR | Внутренняя ошибка без раскрытия деталей |

## Состояние MVP

Один процесс Uvicorn и один worker. Снимок хранится в памяти; после перезапуска нужна повторная загрузка. CSV находятся раздельно в out/api/<analysis_id>/. Старые версии сохраняются для уже начатых скачиваний; автоматической очистки версий пока нет. Временные загрузки удаляются после успеха и ошибок. Не изменяйте каталоги версий во время работы сервера.


## POST /api/ask

Content-Type: application/json. Требуются analysis_id и question. context_gids — от 1 до 5 уникальных существующих gid, строго десятичные строки int64. При пустом/отсутствующем context_gids — 422 INVALID_QUESTION с просьбой выбрать узлы на графе. Вопрос проверяется после удаления начальных и конечных пробелов: от 1 до 2000 символов. Не преобразовывайте gid через JavaScript Number.

```json
{
  "analysis_id": "ТЕКУЩИЙ_ID",
  "question": "Почему этот узел в топе?",
  "context_gids": ["100000003684369100"]
}
```

Можно спрашивать о роли, приоритете или получателях выбранных узлов. Ниже иллюстрация структуры ответа, **не результат реального вызова провайдера**; конкретный текст зависит от LLM:

```json
{
  "analysis_id": "ТЕКУЩИЙ_ID",
  "answer": "У gid=100000003684369100 наблюдаются признаки сбора переводов. Приоритет требует проверки по показанным фактам; полные входящие seed неизвестны.",
  "references": [
    {
      "gid": "100000003684369100",
      "facts": ["Роль: consolidator", "Входящих контрагентов: 24"]
    }
  ],
  "limitations": ["Внешние входящие seed неполны; отношение out/in не трактуется", "Проверка ссылок не гарантирует истинность всего свободного текста модели; сверяйте объяснение с фактами и карточками"]
}
```

facts — серверные строки по текущим данным, включая роль, оценки, степени, суммы, глубину, seed, топ-позицию и показанные связи. Состав не ограничивается двумя фактами из примера. limitations также собирает сервер. Успешный ответ содержит хотя бы одну ссылку; ссылки могут указывать на выбранные узлы и их переданных модели непосредственных соседей. Frontend делает gid кликабельными, выводит ограничения и отображает answer как текст без исполнения HTML.

Контекст: до пяти выбранных узлов, пяти соседей, десяти близких рёбер и 32 KiB JSON. Если связи усечены, limitations явно сообщает число показанных рёбер и предупреждает о неполном списке контрагентов. Модель получает готовые агрегаты/ранжирование, а не весь датасет. Сервер проверяет структуру ответа и принадлежность ссылок контексту; это **не доказательство истинности всей интерпретации модели**.

Сервер использует один снимок и сверяет analysis_id до и после вызова. При 409 STALE_ANALYSIS обновите GET /api/analysis и предложите повторить вопрос. При 503 AI_UNAVAILABLE граф, карточки и CSV остаются доступными. Автоматического повторного запроса к модели нет. Модель приложения настраивается отдельно от Codex CLI через OPENAI_MODEL.

## Временные наблюдения (фича №6)

Новых маршрутов нет. `GET /api/analysis` дополнен `temporal_summary`: `rapid_outflow`, `synchronized_inflow`, `activity_spike` — полные количества наблюдений каждого типа; `n_nodes` — число уникальных узлов с хотя бы одним наблюдением. Один узел может иметь несколько типов и дат. Все четыре значения — целые числа, рассчитанные до ограничения карточек.

`GET /api/nodes/{gid}` дополнен `temporal_patterns`:

- `items`: максимум 50 наблюдений узла из того же analysis_id;
- `total_count`: полное число наблюдений этого узла до усечения;
- `truncated`: true ровно когда total_count > 50.

Порядок: дата по возрастанию; при одинаковой дате — rapid_outflow, synchronized_inflow, activity_spike. Для rapid_outflow дата — день поступления D. Даты outgoing_days идут по возрастанию, sender_gids отсортированы по числовому int64 до преобразования в строки. Для одного узла, даты и вида существует максимум одно наблюдение. Перестановка строк transactions результат не меняет. Пагинации наблюдений пока нет; усечённые элементы остаются в снимке и учитываются в temporal_summary.

Общие поля каждого элемента:

| Поле | Тип | Значение |
|---|---|---|
| kind | enum string | rapid_outflow / synchronized_inflow / activity_spike; discriminator в OpenAPI |
| date | string, YYYY-MM-DD | Дата поступления для rapid_outflow; день наблюдения для остальных |
| explanation | string | Интерпретация как наблюдаемого совпадения или эвристики |
| limitations | array[string] | Ограничения периода, выборки, дневной точности, seed и конкретного вида |

Идентификатор самого узла — прежний `node.gid` карточки, точная строка. Он не повторяется в каждом элементе. `sender_gids[]` — тоже точные десятичные строки, никогда не Number/float.

### rapid_outflow

Одно наблюдение на (gid, D), если за D есть входящие от других участников и исходящие другим участникам за D+1 либо D+2. Self-loop исключён из обеих частей. Несколько операций за день агрегируются, одинаковые строки сохраняются как отдельные операции.

| Дополнительное поле | Тип | Значение |
|---|---|---|
| incoming_n_tx | integer | Число внешних входящих за D |
| incoming_sum_kzt | number | Их сумма в KZT |
| outgoing_days | array[object] | Только дни с наблюдаемыми внешними исходящими, от одного до двух элементов |
| outgoing_days[].date | string, date | D+1 или D+2 |
| outgoing_days[].interval_days | integer, 1 или 2 | Разница календарных дат |
| outgoing_days[].n_tx | integer | Все внешние исходящие операции за этот день |
| outgoing_days[].sum_kzt | number | Их сумма в KZT |

Это не трассировка конкретных денег: поступившие и перечисленные суммы не сопоставляются. Окна могут пересекаться, а одна операция участвовать в нескольких наблюдениях; суммы наблюдений нельзя складывать как независимые потоки. Операции одного дня не устанавливают порядок. Интервал в календарных днях не означает точное число прошедших часов. За концом июля операции неизвестны; частичное окно у границы отмечается в limitations. Для seed входящие неполны.

### synchronized_inflow

Одно наблюдение на узел и день при поступлениях минимум от трёх разных внешних отправителей. Повторные операции отправителя увеличивают n_tx и сумму, но не n_senders; self-loop исключён.

| Дополнительное поле | Тип | Значение |
|---|---|---|
| sender_gids | array[string] | Все разные внешние отправители за этот день |
| n_senders | integer | Их число, минимум 3 |
| n_tx | integer | Число входящих от этих отправителей за день |
| sum_kzt | number | Входящая сумма от этих отправителей |

Совпадение по дню не доказывает координацию участников; времени суток нет.

### activity_spike

Число операций узла за день — входящие и исходящие; self-loop учитывается один раз, включая сумму. Период общий для всех узлов: 2026-07-01 — 2026-07-31 включительно, 31 день. Среднее = period_n_tx / period_days, включая дни без операций. Отбор: n_tx >= 5 и n_tx >= 3 × среднее, обе границы включительны. Сравнение делается по целым счётчикам без ошибки округления среднего. При нуле операций наблюдений нет.

| Дополнительное поле | Тип | Значение |
|---|---|---|
| n_tx | integer | Все операции узла за день с однократным self-loop |
| sum_kzt | number | Их сумма в KZT |
| period_start, period_end | string, date | Обе включительные границы периода |
| period_days | integer | Число календарных дней, сейчас 31 |
| period_n_tx | integer | Все операции узла за весь период |
| average_daily_n_tx | number | Среднее с учётом нулевых дней |
| multiple | number | n_tx / average_daily_n_tx |
| min_daily_n_tx | integer | Применённый минимальный порог, 5 |
| min_multiple | integer | Применённый минимальный коэффициент, 3 |

Это эвристический всплеск относительно среднего той же выборки, не подтверждённая подозрительная операция и не сравнение с внешней нормой.

Расчёт выполняется один раз внутри AnalyzeDataset по уже прочитанным transactions, с агрегацией узлов и дней; карточки ничего не перечитывают и не пересчитывают. Суммы складываются как Decimal с precision=400; HTTP отдаёт суммы числом для отображения, по прежней политике API. Точность, отсутствующая в исходном float64, не восстанавливается. Роли, priority_score, AI-контекст и три CSV не меняются. Временные находки не определяются из агрегированных edges и не добавляются к их оборотам.
