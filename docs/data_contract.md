# API контракт для фронтенда и бэкенда

Версия: MVP v1. Бэкенд обслуживает страницу и API с одного локального адреса. Фронтенд вызывает относительные URL `/api/...`; CORS не требуется. `gid` — целое число. Суммы указаны в KZT. Примеры идентификаторов ниже условные.

## Пользовательский сценарий

1. При открытии страницы вызвать `GET /api/analysis`. Если анализа пока нет — показать форму загрузки трёх файлов.
2. Пользователь загружает `nodes`, `edges`, `transactions` в CSV или Parquet через `POST /api/analyze`.
3. После успешного ответа повторно вызвать `GET /api/analysis` и обновить граф, топ-лист, фильтры и карточку. При ошибке оставить прежний анализ на экране.
4. Поиск `gid` выполняется мгновенно в массиве `nodes`; для полной карточки и связей вызвать `GET /api/nodes/{gid}`.
5. Вопрос к ИИ отправить в `POST /api/ask` с текущим `analysis_id`. Упомянутые в ответе `gid` сделать кликабельными.
6. CSV скачивать по маршрутам `/api/exports/...`.

## 1. Проверка сервера

`GET /api/health` → `200 OK`

```json
{
  "status": "ok",
  "analysis_ready": true,
  "ai_configured": true
}
```

`ai_configured` показывает наличие настроенного доступа к модели, а не гарантирует доступность внешнего сервиса.

## 2. Загрузка и пересчёт данных

`POST /api/analyze` — `multipart/form-data`. Ровно три поля с файлами:

| Поле формы | CSV-колонки или Parquet-поля |
|---|---|
| `nodes` | `gid,depth,is_seed` |
| `edges` | `src,dst,sum_kzt,n_tx,depth` |
| `transactions` | `src,dst,date,sum_kzt` |

Для CSV: UTF-8, первая строка — заголовки, дата — `YYYY-MM-DD`, разделитель — запятая. Для каждого поля допускается `.csv` или `.parquet`. Дополнительные колонки игнорируются; обязательные должны присутствовать и иметь корректные типы. Число узлов не фиксировано в коде. Бэкенд проверяет связи между файлами до замены активного анализа.

Успех → `200 OK` после окончания расчёта:

```json
{
  "analysis_id": "a1b2c3",
  "status": "ready",
  "summary": {
    "n_nodes": 2248,
    "n_edges": 3119,
    "n_transactions": 4840,
    "n_seed": 81,
    "n_clusters": 35,
    "edge_volume_kzt": 365890012.0
  },
  "analysis_url": "/api/analysis"
}
```

Число кластеров здесь только пример: интерфейс отображает фактическое значение ответа. Пока запрос выполняется, кнопка загрузки заблокирована и показан индикатор «Анализируем». При ошибке прежний анализ остаётся доступным.

Если результатов пока нет → `404` с кодом `NO_ANALYSIS`.

## 4. Карточка узла и его связи

`GET /api/nodes/{gid}` → `200 OK`

```json
{
  "analysis_id": "a1b2c3",
  "node": {
    "gid": 101,
    "depth": 2,
    "is_seed": false,
    "role": "consolidator",
    "role_score": 0.84,
    "cluster_id": 3,
    "priority_score": 0.91,
    "evidence": "Признаки консолидации: 11 плательщиков, получено 1 200 000 KZT",
    "in_deg": 11,
    "out_deg": 2,
    "in_kzt": 1200000.0,
    "out_kzt": 100000.0,
    "truncated_by_depth": false
  },
  "incoming": [
    { "src": 202, "dst": 101, "sum_kzt": 50000.0, "n_tx": 2 }
  ],
  "outgoing": [
    { "src": 101, "dst": 303, "sum_kzt": 100000.0, "n_tx": 1 }
  ]
}
```

Неизвестный `gid` → `404` с кодом `GID_NOT_FOUND`.

## 5. Вопрос к ИИ

`POST /api/ask` — `application/json`

```json
{
  "analysis_id": "a1b2c3",
  "question": "Почему gid 101 в топе?",
  "context_gids": [101]
}
```

`context_gids` — выбранные в интерфейсе узлы, может быть пустым массивом. Фронтенд не отправляет все рёбра модели. Бэкенд сам извлекает нужные факты из текущего графа и вызывает выданную LLM.

Успех → `200 OK`:

```json
{
  "analysis_id": "a1b2c3",
  "answer": "У gid 101 есть признаки консолидации: он получил переводы от 11 плательщиков на 1 200 000 KZT. Это основание для проверки, а не вывод о виновности.",
  "references": [
    { "gid": 101, "facts": ["in_deg=11", "in_kzt=1200000"] }
  ],
  "limitations": ["Видны только переводы внутри предоставленной сети"]
}
```

Фронтенд выводит `answer`, делает `references[].gid` ссылками на карточку и показывает `limitations` под ответом. Бэкенд проверяет, что упомянутые `gid` существуют в текущем анализе. Если модель не отвечает → `503` с кодом `AI_UNAVAILABLE`; граф и CSV остаются доступными. Если анализ уже заменён → `409` с кодом `STALE_ANALYSIS`, после чего фронтенд обновляет `GET /api/analysis`.

## 6. Скачивание результатов

- `GET /api/exports/nodes_roles.csv`
- `GET /api/exports/clusters.csv`
- `GET /api/exports/top_nodes.csv`

Успех → `200 OK`, `Content-Type: text/csv; charset=utf-8`, `Content-Disposition: attachment`. Возвращаются файлы текущего `analysis_id`. Нельзя принимать произвольное имя файла из URL; только три указанных имени.

## Единый формат ошибки

```json
{
  "error": {
    "code": "INVALID_SCHEMA",
    "message": "В nodes.csv отсутствует обязательная колонка depth",
    "details": {
      "file": "nodes.csv",
      "missing_columns": ["depth"]
    }
  }
}
```

`422 INVALID_SCHEMA` — неверные файлы или данные; `404 NO_ANALYSIS/GID_NOT_FOUND` — нет результата или узла; `409 STALE_ANALYSIS` — вопрос относится к старому набору; `503 AI_UNAVAILABLE` — недоступна модель. Не отдавать пользователю traceback и токен API.

## Что можно делать параллельно

- Фронтендер 1: `GET /api/analysis` → граф, поиск `gid`, цвета ролей, стрелки, фокус на выбранном узле.
- Фронтендер 2: форма трёх файлов → `POST /api/analyze`; топ, карточка через `GET /api/nodes/{gid}`; вопрос к ИИ через `POST /api/ask`; кнопки скачивания.
- Пока backend не готов, фронтенд использует объекты-примеры из этого файла как mock. Названия маршрутов и полей не менять без общего согласования.
